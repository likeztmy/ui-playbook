# Drawer / Sheet: what stays usable behind it

Research for backlog topic *Drawer / Sheet* (rank 5 in `docs/plans/2026-10-27-topic-priorities.md`; scoped in `2026-10-25-topic-backlog.md`, "### Drawer / Sheet"). The claim to test: what matters about a sheet is whether the task behind it stays usable (modal vs non-modal, Material's "standard"), not which edge it slides from. Planned demo: a map with route details in a bottom sheet, where only modality changes. Post uses no sheet anywhere today. On a phone (container ≤ 760px) a message and a new message each replace the list as a full page; folders become an anchored menu in the list bar; rows have a context menu; an attachment opens in a Dialog (§7).

Not repeated here:
- Scrim, alert dialog vs task dialog, initial focus, Escape, focus return and "one dialog never opens over another" are on `src/pages/components/dialog.mdx`.
- Access cost decides memory use (Gray, Sims, Fu & Schoelles 2006: a 200 ms lockout drops looks from 5.6 to 4.8 per trial; Ballard 1995 via Gray) is in `2026-10-26-layout-and-guidance.md` §10, and belongs to the backlog page *Keep the comparison in sight*. This note adds two sources to it (§5.2) and cites it only by reference.
- Fluid-motion vocabulary (springs, interruptibility) belongs to the motion topics. Only the numbers that decide where a sheet lands are here.

**Labels.**

- **Secondary**: known only from press, a third-party guide, or a paper citing the claim.
- **Unverified**: from memory or inference. Keep off pages.

## 1. What the two systems say a sheet is

### Material 3

- **Material 3, *Bottom sheets: guidelines*** (https://m3.material.io/components/bottom-sheets/guidelines). **Verified.**
  - Standard sheets "co-exist with the screen's main UI region". They allow "simultaneously viewing and interacting with both regions", especially when the main region "is frequently scrolled or panned". The named example is "location information over a map".
  - Modal sheets, "like dialogs", are "disabling all other app functionality". Suggested use: a menu, "an alternative to inline menus or simple dialogs on mobile". "Modal bottom sheets are used in mobile apps only."
  - A modal sheet's initial position "is capped at 50% of the screen height"; longer content is pulled up and scrolled.
  - Dismissal: tap an item, "Tapping the scrim", swipe down, or a close affordance. The scrim click should "always close the bottom sheet".
  - Drag handle: "Selecting the drag handle should toggle through preset heights or close the sheet". Without a handle, Material "requires the inclusion of a single-pointer alternative" for changing height.
  - On larger windows a bottom sheet "can be swapped for a side sheet".
- **Material 3, *Bottom sheets: specs*** (https://m3.material.io/components/bottom-sheets/specs). **Verified.** "Modal bottom sheets are above a scrim while standard bottom sheets don't have a scrim. Besides this, both variants … have the same specs." Full width "up to 640dp", top margin 72dp (56dp past 640dp), drag-handle padding 22dp.
- **Material 3, *Side sheets: guidelines*** (https://m3.material.io/components/side-sheets/guidelines). **Verified.**
  - Standard side sheets "remain visible while people interact with primary content". Typical uses are filters and supplemental details.
  - "Modal side sheets are preferred in compact breakpoints, like mobile, due to limited screen size." They hold "the same kinds of content". A video caption: modal on small screens "can transition to standard side sheets at larger screen sizes".
  - A standard side sheet takes space rather than covering it: "the body area shrinks to accommodate the sheet's width".
  - **So in Material, the same content changes modality with window size.** Modality follows how much of the parent would stay visible, not the task.

### Apple

- **Apple HIG, *Sheets*** (https://developer.apple.com/design/human-interface-guidelines/sheets; change log to 24 Mar 2026). **Verified.**
  - "In macOS, tvOS, visionOS, and watchOS, a sheet is always modal." Only iOS and iPadOS allow nonmodal sheets. The example is the Notes format sheet: "people can make additional text selections without dismissing the sheet."
  - "Use a nonmodal view when you want to present supplementary items that affect the main task in the parent view". The alternatives named are a split view on visionOS and a panel on macOS.
  - macOS: "Use a panel instead of a sheet if people need to repeatedly provide input and observe results". The example is find and replace.
  - Detents: large is full height; medium is "about half of the fully expanded height". Mail and Messages compose "display only at full height".
  - Grabber: people "can also tap it to cycle through the detents", and it "works with VoiceOver".
  - "Support swiping to dismiss a sheet." If there are unsaved changes, confirm with an action sheet.
  - visionOS: "Avoid displaying a sheet that emerges from the bottom edge of a window."
- **Apple HIG, *Modality*** (https://developer.apple.com/design/human-interface-guidelines/modality). **Verified.** Modality is defined as a mode that "prevents interaction with the parent view and requires an explicit action to dismiss". The guidance: "Present content modally only when there's a clear benefit", and keep the task short, or people "can lose track of the task they suspended".

### Verdict on the edge

- Neither system ties meaning to the edge. Material swaps bottom for side by window width with the same content. Apple centres sheets on visionOS and drops the bottom edge there. Material's side-sheet placement is a layout rule: right, "to avoid interference with any navigational components on the left edge". **The working claim survives on this point.**

## 2. Modality is set per height, not per component

This is the strongest finding, and it changes the demo.

- **UIKit, `largestUndimmedDetentIdentifier`** (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/largestundimmeddetentidentifier). **Verified.**
  - The default is `nil`: "the system adds a noninteractive dimming view underneath the sheet at all detents."
  - Set it to `.medium` and dimming is added only at `.large`. "Without a dimming view, the undimmed area around the sheet responds to user interaction".
  - **One sheet is non-modal at half height and modal at full height.**
- **WWDC21, *Customize and resize sheets in UIKit*** (session 10063, https://developer.apple.com/videos/play/wwdc2021/10063/, transcript). **Verified.**
  - The property shipped as `smallestUndimmedDetentIdentifier` and was renamed later. "Dimming still fades in if I resize to the large detent."
  - It is more than visual: "I can now interact not only with the content in the sheet but also with the content outside of the sheet."
  - Apple's own pitch: "If you have any half height custom cards in your apps today, replace them".
- **SwiftUI, `presentationBackgroundInteraction(_:)`** (iOS 16.4; https://developer.apple.com/documentation/swiftui/view/presentationbackgroundinteraction(_:)). **Verified.** "SwiftUI automatically disables the view behind a sheet". The doc example is `.enabled(upThrough: .height(120))` with detents `[.height(120), .medium, .large]`: the background is interactive only at the smallest height.
- **vaul, `fadeFromIndex`** (https://github.com/emilkowalski/vaul/blob/main/src/index.tsx). **Verified (source).** "Index of a `snapPoint` from which the overlay fade should be applied". The default is the last snap point. vaul's `modal` is a separate boolean, though, so the overlay can fade in while outside clicks stay blocked, or the reverse. **The web library lets the look and the behaviour disagree; Apple's API makes them one property.**
- **NN/g, Laubheimer, *Bottom Sheets: Definition and UX Guidelines*** (11 Jun 2023, https://www.nngroup.com/articles/bottom-sheet/). **Verified (article; qualitative, no counts).** "Expandable sheets usually start nonmodal when minimized and become modal when expanded" (paraphrase of the article's point, not a quote).
- **What this does to the claim.** The claim is right that modality matters more than the edge. But the platforms treat modality as a function of how much of the parent is left to use, not as a fixed property of the sheet. A sheet that covers the map is modal whether or not it says so. **Refined claim: a sheet should block the task behind it exactly when it covers it.**

## 3. The web platform and the libraries

### Platform

- **HTML, the `dialog` element** (https://html.spec.whatwg.org/multipage/interactive-elements.html). **Verified.**
  - `showModal()` puts the dialog in the top layer and blocks the document, which makes outside content inert. `show()` only "Displays the dialog element".
  - `closedby`: the default "Auto state behaves as Close Request state" for `showModal(), otherwise the None state`. **A non-modal `<dialog>` opened with `show()` ignores Escape and Android Back by default.** It closes on them only with `closedby="closerequest"` or `"any"`.
  - `show()` still runs the dialog focusing steps, so focus moves into it.
  - The spec warns that "context menus, tooltips, and popup listboxes are not dialog boxes".
- **WAI-ARIA APG, *Dialog (Modal) Pattern*** (https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). **Verified.**
  - "Like non-modal dialogs, modal dialogs contain their tab sequence". The difference is that modal dialogs "do not provide means for moving keyboard focus outside the dialog window without closing" it. **So a non-modal sheet needs an explicit way to move focus out and back**: a key such as F6, or a landmark the screen-reader user can jump to. Plain Tab containment isn't the distinction.
  - Set `aria-modal="true"` "only when both" of these hold: code blocks every outside interaction, and styling obscures it. Otherwise users of some assistive technologies face "severe negative ramifications".
  - **Consequence for per-detent modality (§2):** `aria-modal`, `inert` and the focus trap must flip together when the sheet crosses the detent. A scrim that fades in without `inert`, or `inert` with no scrim, is exactly the mismatch APG warns about.

### Base UI (`@base-ui/react` 1.9.0, installed in this repo)

- **Base UI, Drawer** (https://base-ui.com/react/components/drawer; source https://github.com/mui/base-ui/tree/master/packages/react/src/drawer). **Verified (docs and source, matched against `node_modules`).**
  - It ships a Drawer built on Dialog that "adds gesture support, snap points, and indent effects".
  - `modal` takes three values:
    - `true` (default): focus trapped, scroll locked, outside pointer disabled.
    - `false`: outside interaction allowed.
    - `'trap-focus'`: focus trapped, but outside pointer and scroll stay live.
  - **A `modal={false}` drawer still closes on an outside press, and on focus leaving it, by default.** From `DrawerRoot.d.ts`: `disablePointerDismissal` "also prevents the drawer from closing when focus moves outside". A map demo built naively on `modal={false}` would close the route sheet on the first tap on the map. That is Material's *modal* behaviour.
  - `snapPoints` take fractions (0–1), pixels or rem. `snapToSequentialPoints` "Disables velocity-based snap skipping".
  - It handles Android Back through `CloseWatcher`, on Android only, so it doesn't change desktop Escape.
  - `Drawer.VirtualKeyboardProvider` sets `--drawer-keyboard-inset` and keeps the focused field visible.
- **vaul** (https://github.com/emilkowalski/vaul). **Verified (source and README).**
  - The README says "This repo is unmaintained" (last push 3 Oct 2025).
  - `modal={false}` cancels both `onPointerDownOutside` and `onFocusOutside`, so it doesn't light-dismiss. That is the opposite default from Base UI's `modal={false}`.
  - **The same word, `modal={false}`, means "light-dismiss popover" in one library and "standard sheet" in the other.**

## 4. Gesture mechanics, with numbers

### Where a release lands

| | Fling threshold | Distance threshold | Velocity measured as | Source |
| --- | --- | --- | --- | --- |
| Material `BottomSheetBehavior` | `DEFAULT_SIGNIFICANT_VEL_THRESHOLD = 500`, in **device px/s** (`computeCurrentVelocity(1000, …)`) | hide if projected top `top + yvel × 0.1` sits more than `HIDE_THRESHOLD = 0.5` of the peek below collapsed, or released below the midpoint | release velocity | `BottomSheetBehavior.java`, **Verified** |
| Base UI Drawer | `FAST_SWIPE_VELOCITY = 0.5` px/ms; snap skipping from `SNAP_VELOCITY_THRESHOLD = 0.5`, offset `v × 300` px (v capped at 4) | dismiss past 50% of the sheet's size (minimum 10px) | release velocity from recent samples (≤ 80 ms old) | `DrawerViewport.tsx`, `useSwipeDismiss.ts`, **Verified** |
| vaul | `VELOCITY_THRESHOLD = 0.4` px/ms; above 2 px/ms jumps to the first or last snap point | `CLOSE_THRESHOLD = 0.25` of visible height | **average** velocity: total distance ÷ total drag time | `constants.ts`, `index.tsx`, `use-snap-points.ts`, **Verified** |

- **Computed: the same number isn't the same speed.**
  - Base UI's 0.5 px/ms is 500 CSS px/s.
  - Material's 500 is in device pixels. At 2.625× density (a common xxhdpi phone) it is 500 ÷ 2.625 ≈ **190 dp/s**; at 3.5× it is ≈ **143 dp/s**.
  - So Material's fling threshold is roughly a third of the web's in physical speed, and varies by phone.
  - vaul averages over the whole drag. A slow start followed by a quick flick reads slower than it felt, so a 0.4 px/ms average needs a faster release than the number suggests.
- **Material's hide decision projects the release.** It adds 0.1 s of the current velocity to the position (`HIDE_FRICTION = 0.1`) and judges the projected point. That is the idea WWDC18 *Designing Fluid Interfaces* (session 803, transcript, **Verified**) calls "a projection": decide by where a throw would land, not where the finger let go.
- **Default heights.**
  - Material: auto peek is "the 16:9 ratio keyline of its parent", `max(64dp, H − W·9/16)`. Half-expanded ratio is 0.5. Compose `BottomSheetDefaults.SheetPeekHeight = 56.dp` and `SheetMaxWidth = 640.dp` (androidx `SheetDefaults.kt`). **Verified (source).**
  - **Computed:** on a 412 × 915 dp phone, auto peek leaves a 412 × 232 dp strip of the parent visible (25% of the height), and the sheet takes 683 dp.
  - Apple's medium detent is "approximately half the height of the screen, and is inactive in compact height" (`UISheetPresentationController.Detent.medium()`, **Verified**). Material caps a modal sheet's first position at 50% too.
  - **In landscape on a phone, the medium detent disappears.** By default the sheet then goes full-screen (`prefersEdgeAttachedInCompactHeight` defaults to `false`, **Verified**). A non-modal half sheet turns into a full-screen one when the phone is rotated.

### Scroll inside the sheet vs dragging the sheet

- **Apple: scrolling grows the sheet first.** `prefersScrollingExpandsWhenScrolledToEdge` defaults to `true`: scrolling up raises the detent "instead of scrolling the sheet's content". Apple's advice is to set it to `false` "on a nonmodal sheet to avoid obscuring the content underneath" (**Verified**). SwiftUI's `presentationContentInteraction(.scrolls)` does the same; "People can always resize your presentation using the drag indicator" (**Verified**). **The default is designed for modal sheets. In a non-modal sheet, a scroll that grows the sheet covers the map the person is using.**
- **Material.** Downward drags move the sheet only when the inner list can't scroll up any further (`if (!canScrollUp)`). A touch on the drag handle always drags the sheet, even over scrollable content (**Verified, source**).
- **Base UI.** Axis lock after `AXIS_LOCK_SLOP = 6` px. The cross axis wins only if it leads by `AXIS_LOCK_BIAS = 2` px. Until either axis passes 6px the event is left alone, because on iOS "`preventDefault()` on the first cancelable touchmove cancels native scrolling for the entire gesture" (source comment, **Verified**). Opt-outs: `data-base-ui-swipe-ignore`, or `="x"`/`="y"` for carousels.
- **vaul.**
  - No drag for 500 ms after opening.
  - No drag while text is selected.
  - Inside a scroller that isn't at `scrollTop 0`, no drag.
  - After a scroll, drag stays locked for `SCROLL_LOCK_TIMEOUT = 100` ms, so the end of a scroll can't become a dismiss.
  - (**Verified, source.**)

### Rubber-banding (dragging past the last height)

- **Base UI:** against the allowed direction, displacement is `sign(d)·|d|^0.5` (`applyDirectionalDamping`). **Computed:** 100px of finger travel moves the sheet 10px; 400px moves it 20px.
- **vaul:** `8 · (ln(d + 1) − 2)`. **Computed:** 100px → 20.9px, 400px → 32.0px.
- **Material:** none; an upward drag clamps at the expanded offset (**Verified, source**).
- Apple's sheet resistance curve isn't documented. The often-quoted UIScrollView constant 0.55 is reverse-engineered (**Unverified**).

### The keyboard

- **UIKit:** medium sheets "support automatic keyboard avoidance": the sheet grows for the keyboard and "automatically collapses back down" (WWDC21 10063, **Verified**).
- **vaul** watches `visualViewport`. It counts the keyboard as opened or closed only on a height change of 60px or more. With `repositionInputs` it shrinks the drawer instead of moving it up (**Verified, source**).
- **Base UI** offers the opt-in `VirtualKeyboardProvider` and `--drawer-keyboard-inset` (**Verified**).
- **Consequence:** a sheet with a search field can't stay at half height while typing on a phone. The keyboard takes roughly the bottom half, and the sheet grows into the map either way. The map demo should keep text input out of the sheet, or own this case.

### Back

- **Android predictive back** (https://developer.android.com/design/ui/mobile/guides/patterns/predictive-back). **Verified.**
  - Bottom and side sheets get the animation from MDC 1.10.0-alpha02.
  - Full-screen surfaces scale "100% → 90%". The fade-through starts "at the 35% progress threshold".
  - No numeric commit point is given.
  - Material sheets detach from the side edges (bottom sheet) or the top and bottom (side sheet) "to signal it will close".
- **Base UI** wires Back to the topmost open drawer via `CloseWatcher` (**Verified**).
- **NN/g:** some users "may not realize they are in a bottom sheet" and press Back expecting page navigation (**Verified, qualitative**).

## 5. Human evidence

### 5.1 Reach: the bottom edge isn't the point

- **Hoober 2013**, *How Do Users Really Hold Mobile Devices?*, UXmatters (https://www.uxmatters.com/mt/archives/2013/02/how-do-users-really-hold-mobile-devices.php). **Verified (author's article; field observation, not peer-reviewed; foundational).**
  - 1,333 observations, 780 of them touching the screen: 49% one-handed, 36% cradled, 15% two-handed.
  - Grips changed "sometimes every few seconds".
  - The current page's editor's note says the author considers it superseded and the reach drawings inaccurate.
- **Hoober 2017**, *Design for Fingers, Touch, and People, Part 1*, UXmatters (https://www.uxmatters.com/mt/archives/2017/03/design-for-fingers-touch-and-people-part-1.php). **Verified (article).**
  - People "prefer to view and touch the center of the screen".
  - Targets can be "as small as 7 millimeters" in the centre but "about 12 millimeters" in the corners.
  - The thumb-sweep chart is "well-known, but incorrect".
- **Le, Mayer, Bader & Henze 2018**, *Fingers' Range and Comfortable Area for One-Handed Smartphone Interaction Beyond the Touchscreen*, CHI '18, https://doi.org/10.1145/3173574.3173605 (open PDF from LMU). **Verified (full text).**
  - 16 participants, motion capture, four phones.
  - The thumb's comfortable area (reach without losing grip) was 33.6, 41.9, 35.2 and 35.0 cm² on phones of 76.6, 95.9, 116.1 and 132.2 cm².
  - "the grip shifts towards the top edge with increasing phone sizes."
  - **Computed:** the thumb covers 44% of the smallest phone's face but **26% of the largest**. The area doesn't grow with the phone; the phone grows around it.
- **NN/g 2023** (above): the idea that sheets improve reach is "largely incorrect".
- **What this means for the claim.** A bottom sheet does put its first items near the thumb on a big phone. But its dismiss controls (Apple puts Cancel at the top leading edge) land outside the comfortable area at the large detent. That is why both systems make swipe-down and scrim-tap the dismissals, and why Material requires the handle to be tappable (inference). The edge decides where things are reachable, not what the sheet does to the task.
- **No 2020+ peer-reviewed thumb-reach study was found** (searches 2026-10-27: Europe PMC, web). Le 2018 is the most recent primary measurement read.

### 5.2 Keeping the map in sight

- **Plumlee & Ware 2006**, *Zooming versus multiple window interfaces: Cognitive costs of visual comparisons*, ACM TOCHI 13(2), https://doi.org/10.1145/1165734.1165736. **Verified (abstract).**
  - Comparisons done by navigating (zooming) had "much higher" error rates than with extra windows reached by eye movement.
  - With eye movements, people made "far more visits back and forth". Only "a single graphical object was held in visual working memory".
  - Their heuristic: extra windows are needed when the comparison exceeds what visual working memory holds.
- **Draschkow, Kallmayer & Nobre 2021**, *When natural behavior engages working memory*, Curr. Biol. 31(4):869, https://doi.org/10.1016/j.cub.2020.11.013 (PMC7902904). **Verified (full text).** 24 participants copied object layouts in VR, with the model at 0°, 45°, 90° or 135° from the workspace. As looking cost more locomotion, reliance on working memory rose "in a shallow and linear fashion". Reliance stayed below lab capacity measures. People prefer to look again.
- **Applied to the map (inference; no sheet study exists).**
  - A modal route sheet turns "glance at the map" into dismiss, look, reopen: two actions per look instead of one eye movement.
  - Gray et al. 2006 (layout-and-guidance §10) show that far smaller costs (200 ms) already reduce looking.
  - Plumlee & Ware show that the switch to memory costs accuracy.
  - The comparison here is "does this turn match that street", which needs both in view at once.
- **No study of modal vs non-modal sheets, or of bottom sheets at all, was found** (Europe PMC, ACM via web search, 2026-10-27).

### 5.3 Mode errors

- **Sellen, Kurtenbach & Buxton 1992**, *The prevention of mode errors through sensory feedback*, Human–Computer Interaction 7(2):141, https://doi.org/10.1207/s15327051hci0702_1. **Verified (abstract); foundational.** Kinesthetic feedback beat visual feedback at preventing mode errors. A non-latching pedal, held by the user, beat a latching one: "user-maintained mode states prevent mode errors more effectively".
- **Applied (inference).**
  - A sheet the finger is holding is a user-maintained mode. A sheet left at a detent is system-maintained, so the scrim is the only cue to which mode is on.
  - Per-detent modality (§2) gives two modes for one object. The dim is the only visual cue to which one is live, so dim and `inert` must change on the same frame.
  - The error to expect in a modal sheet: a tap on the map meant to pick another place is spent on dismissing (Material's scrim always closes). The new place isn't selected.
- **NN/g's three observed failures** (qualitative): no clear way to dismiss, stacked sheets, "Obscuring relevant background content".

## 6. What non-modal costs

- **Dismissal was the feedback.** In WWDC21 10063 the photo picker stops closing once it is non-modal, and then "it's not obvious that anything happened". Apple's fix is to drop the sheet to the medium detent on selection, so the result shows behind it. **Verified.** **A non-modal sheet must show the result of each action in the parent, or move to let it show.** For the map: tapping another place must visibly retarget the sheet's contents and the map's highlight together.
- **Two live regions.**
  - Escape: a `show()` dialog ignores it by default (§3).
  - Back: Base UI handles it on Android only.
  - Keyboard users need a documented hop between the regions. APG implies one exists for non-modal dialogs but doesn't name the key.
  - Screen readers: with no `aria-modal`, the sheet should be a labelled region or non-modal dialog reachable from the landmarks, and focus mustn't be stolen when the map selection changes. "Feedback without stealing focus" is a separate backlog topic.
- **Covering is still covering.** At the large detent the map is gone, whatever the flags say. Every system read here dims at full height. Making a full-height sheet non-modal gives interaction with something no one can see.
- **Platform limits.** macOS and visionOS sheets are always modal; their non-modal tool is a panel or split view. A page must not offer the iOS non-modal sheet as the desktop answer. Material does the same by size: compact means modal, larger means standard.

## 7. Post (Measured)

- **Phone layout.** `Shell.module.scss` `@container (max-width: 760px)`: one grid area; `.side` (folders) hidden; the folder name becomes a `Menu` trigger in the list bar (`Shell.tsx` 101–116); New message shows its icon only; density toggle hidden.
- **A message.** `post.open` replaces the list in `main` (`Conversation … single`, `data-view="message"`). It is a pushed page, not a sheet. Back puts focus on the row (`Shell.tsx` 79–89). Reference: iOS Mail pushes the message too. **Should not become a sheet.**
- **Compose.**
  - A new message is a full page in `main` (`Composer page`). Escape calls `onBack` (`Composer.tsx` 108). Leaving keeps a non-empty draft in Drafts (`useCompose.ts` `close`).
  - Reply and forward are inline in the conversation.
  - Reference: Apple's iPhone guide (iOS 12, https://support.apple.com/en-asia/guide/iphone/save-an-email-draft-iph37c056e7/12.0, **Verified**): "Swipe down on the title bar of an email you're writing", then "tap its title at the bottom of the screen" to return. The HIG says Mail's compose sheet displays only at full height.
  - So iOS Mail's compose is a full-height modal sheet with a collapsed state that frees the app behind it. **This is the second case for the page.**
    - In Post on a phone, checking another message while writing a new one means: Back (draft saved), find the message, open Drafts, open the draft. That is four steps and a context loss.
    - A compose sheet that collapses to a bar needs two: swipe down, tap the bar.
  - Gmail on the web uses a minimisable compose window at the bottom right (**Secondary**: third-party guides, 2013).
  - On wide screens Post's composer also replaces the list. The same argument applies, with a docked window instead of a sheet.
- **Menus.**
  - The folder menu is an anchored Base UI `Menu` (`ui/Menu.tsx`: `side="bottom"`, `align="start"`, offset 6) with 5 folders.
  - Material offers a modal bottom sheet as an alternative to menus "especially when offering a long list of action items". Five short items don't qualify. **Keep the menu.**
  - The row context menu (`Line.tsx` 113–131) has 3 items. **Keep it.**
- **Other overlays.** The attachment preview is a `Dialog` (`Attachments.tsx`); the recipients list and link editor are `Popover`s. None calls for a sheet.
- **No Drawer exists in `src/ui/`.** Base UI 1.9.0's Drawer is installed with `@base-ui/react`.

### Folklore vs evidence

| Folklore | Evidence | Verdict |
| --- | --- | --- |
| "Bottom sheets are for thumb reach." | Thumb comfort area is flat at ~35 cm² while phones grow (Le 2018); people prefer the centre (Hoober 2017); NN/g calls the reach argument "largely incorrect". | Mostly wrong |
| "The edge tells you what kind of panel it is." | Material swaps bottom ↔ side by window width with the same content; Apple centres sheets on visionOS. | Wrong |
| "A sheet is modal or it isn't." | UIKit, SwiftUI and vaul set modality per detent; NN/g: nonmodal when minimised, modal when expanded. | Wrong: per height |
| "`modal={false}` makes a standard sheet." | Base UI's non-modal drawer still closes on outside press and focus-out; vaul's doesn't. | Library-dependent |
| "A non-modal `<dialog>` closes on Escape." | `closedby` Auto = None for `show()`. | Wrong by default |
| "Non-modal is always friendlier." | Loses dismissal-as-feedback (WWDC21); full-height non-modal hides what it frees; macOS and visionOS forbid it. | Only while the parent is visible |
| "Fling thresholds are a universal constant." | 500 px/s device pixels (Material) vs 0.5 CSS px/ms (Base UI) vs 0.4 px/ms average (vaul). | Differs up to ~3× |

## Demo ideas

1. **Main comparison, refined.** The same map and route sheet at the same medium height and position, with the same motion. Before: modal at every height (dim plus `inert`, a tap on the map closes the sheet). After: non-modal up to medium, modal at large, the way UIKit's `largestUndimmedDetentIdentifier` does it. The variable is still modality, and the After is what the platforms actually do. Task: "Which of these two cafés is on your route?" The reader has to tap a second place. In the Before that tap is spent on dismissing; in the After the sheet retargets.
2. **The crossing.** Drag the After sheet from medium to large: the dim and `inert` arrive together at the detent and leave together. A small readout shows `aria-modal` and `inert` flipping. This shows the flags are one switch (§2, §3).
3. **Feedback after selection (WWDC21 postcard).** In the non-modal sheet, tapping a stop either does nothing visible (sheet stays, map unchanged) or highlights the stop on the map and nudges the sheet down. Only that changes.
4. **Post compose (second case).** A phone frame. Before: New message as a page; checking the thread you're answering takes Back, find, Drafts, reopen. After: compose as a full-height sheet that swipes down to a bar, with the list live above it (iOS Mail's behaviour). Count the steps on screen.
5. **Detail, not the main comparison: scroll vs grow.** Same non-modal sheet. Scrolling its list either grows the sheet over the map (Apple's default) or scrolls the list (`prefersScrollingExpandsWhenScrolledToEdge = false`, Apple's advice for non-modal).

## What a page can honestly claim

- Material and Apple both separate sheets that block the parent from sheets that don't. Both give the non-modal kind to supplementary content that changes the parent while it stays visible: a map's place details, a format panel. Verified.
- Which edge a sheet comes from carries no meaning in either system; it follows window size and platform. Verified.
- Apple's API, vaul and NN/g's description all make one sheet non-modal at small heights and modal when it covers the parent. A page can recommend "block exactly when you cover". Verified as platform practice; no user study tests it.
- A non-modal sheet has to show the result of each action in the parent, because closing is no longer the confirmation. Apple's WWDC21 example. Verified.
- On the web, the flags have to move together: `aria-modal`, `inert`, the focus trap and the scrim. A non-modal `<dialog>` ignores Escape unless `closedby` says otherwise. Verified (HTML spec, APG).
- Library defaults disagree on what "not modal" means. Verified (Base UI and vaul source).
- Looking costs less than remembering, and errors rise when a comparison needs navigation (Plumlee & Ware 2006; Draschkow 2021; Gray et al. 2006). The page may cite this as the mechanism, **not** as a measured sheet effect.
- It cannot claim that bottom sheets are easier to reach, any number for how much faster a non-modal sheet is, or any study of sheets at all.

## Open questions

- **Does per-detent modality cause mode errors?** People may not notice the dim arriving at the large detent, and then tap where the map was. No study found. Sellen 1992 predicts the dim is weaker feedback than holding the sheet.
- **Is "block when you cover" right for side sheets on tablets?** There, Material shrinks the body instead of covering it, so the question doesn't arise. The page should probably limit the claim to overlays.
- **What threshold should the demo use?** Base UI's 0.5 CSS px/ms is the house library's, so use it unless the reader is meant to feel the difference.
- **Keyboard path for the demo:** F6 or a skip link between map and sheet? Needs a check against what VoiceOver and TalkBack users expect. No primary source was read.
- **Should Post's compose become a sheet on phones?** That is a product change, and it argues against the current "page" decision. It needs the owner's sign-off before it's planned (memory: plan before building features).
- **Thumb reach after 2018:** no peer-reviewed measurement on current 6.7–6.9" phones was found. Worth one more search on ACM DL directly if the page mentions reach at all.
